# Tooling trust boundaries

Current assets are maintained source, exact metadata/schema/lock identities and scoped repository reports. Reviewed executable policy and its independently pinned schema are trusted. Received JSON values are data and cannot choose an executable, repository identity, plugin or weaker policy.

The implemented input boundary refuses duplicate keys, nonfinite values, invalid UTF-8, unpaired surrogates, oversized files and linked/nonregular inputs. Fixed authored diagnostics avoid echoing confidential values. Generation requires accepted metadata and exclusively creates a new caller-chosen output; verification never replaces the canonical inventory.

The tooling assumes a stable ordinary local filesystem and reviewed environment. It does not sandbox hostile concurrent filesystem changes, operating-system compromise or power loss. Static checks do not establish correct confidence mappings, model/data provenance, numerical or statistical validity, physical measurements, deployment safety or future confidence.

Future calibration requires actual labels and raw samples, complete prior shift/placement/trial populations, accepted numerical methods and unchanged threshold policy. A seal cannot supply absent probability support, drop failed curves, convert software into measured fabric, calibrate a meter or certify a deployment.
